# ADR-004: Storage, Vector Retrieval & Memory Strategy

> **Status**: PROPOSED (PENDING OWNER APPROVAL)  
> **Date**: 2026-10-22  
> **Deciders**: Principal Architect & Data/Memory Lead (Subject to Project Owner Review)  
> **Impact Area**: Persistence Layer, Vector Search, Semantic Memory, Checkpointing  

---

## 1. Context & Problem Statement

Project **Javed (New JARVIS)** requires persistent storage across five distinct data domains:
1. **Agent Graph Checkpoints**: Node states, execution history, and interrupted states for LangGraph.
2. **Conversational History**: User messages, agent responses, tool invocation records, and session metadata.
3. **Application & Operational Data**: Tool permissions, user preferences, API cost tracking, and system logs.
4. **Long-Term User Memory**: Extracted user facts, preferences, operational rules, and verified learnings (subject to deduplication, correction, and deletion).
5. **Document Knowledge & Embeddings**: Vectorized chunks of user documents (PDF, DOCX, XLSX) and web crawl results for retrieval-augmented generation (RAG).

We must establish a clean, maintainable persistence architecture without running multiple overlapping database daemons.

---

## 2. Options Considered & Critical Evaluations

### 2.1 Primary Relational Engine: SQLite vs PostgreSQL
- **Development Baseline**: **SQLite** (via Python's `aiosqlite` and `sqlite3`).
  - *Rationale*: Zero external dependencies, file-based (`javed.db`), runs without background daemons, zero configuration required on a Windows non-admin machine. Perfect for local desktop development and single-user personal assistant workflows.
- **Production Target**: **PostgreSQL 16+**.
  - *Rationale*: Enterprise concurrency, robust row-level security, high performance for multi-gigabyte document corpora, native vector search via `pgvector`.
- **Migration Strategy**: Use **SQLAlchemy 2.0 (asyncio)** + **Alembic** migrations. Data models remain agnostic of the underlying relational engine, allowing effortless switching between SQLite (local dev) and PostgreSQL (production).

### 2.2 Semantic Vector Search: pgvector vs Qdrant vs ChromaDB
- **Candidate A: `pgvector` (APPROVED PRODUCTION TARGET)**:
  - Embeds vector search directly inside PostgreSQL using standard HNSW or IVFFlat indexes.
  - *Advantage*: Eliminates the need for a separate vector database server. Transactions span both structured data (e.g. document metadata) and vector embeddings atomically, preventing dual-write inconsistency.
- **Candidate B: `Qdrant` (DEFERRED ALTERNATIVE)**:
  - High-performance, dedicated Rust-based vector search engine with rich filtering.
  - *Evaluation*: Excellent engine, but running a separate Qdrant daemon adds operational overhead for a local desktop assistant. We defer Qdrant until vector scale benchmarks (> 1 million vectors) prove pgvector is insufficient.
- **Candidate C: `sqlite-vec` / `ChromaDB` (INITIAL DEV CANDIDATE)**:
  - For local development with SQLite, `sqlite-vec` (or embedded ChromaDB) allows zero-daemon vector retrieval.
  - *Decision*: Adopt `sqlite-vec` or local embedded vector storage for early development, transitioning cleanly to `pgvector` in PostgreSQL.

### 2.3 Retrieval Frameworks: LangGraph/LangChain vs LlamaIndex
- **Candidate: LlamaIndex (REJECTED)**:
  - *Evaluation*: LlamaIndex provides rich RAG indexing abstractions. However, LangChain Core and LangGraph already include document loaders, text splitters, vector store adapters, and contextual compression retrievers.
  - *Decision*: Introducing LlamaIndex alongside LangGraph creates a severe framework overlap violating Rule 11 ([RULES.md](file:///c:/Users/arehman/Desktop/AI Projects/Javed/docs/RULES.md)). We implement retrieval workflows natively within LangGraph nodes.

## 3. Decision

1. **Relational & State Store**:
   - Initial local development: **SQLite** (`data/javed.db`).
   - Production deployment: **PostgreSQL 16+**.
   - Data access: **SQLAlchemy 2.0 async** with **Alembic** migrations.
2. **LangGraph Checkpoints**:
   - Initial: `SqliteSaver` (from `langgraph.checkpoint.sqlite`).
   - Production: `PostgresSaver` (from `langgraph.checkpoint.postgres`).
3. **Vector Retrieval**:
   - Initial: Embedded vector storage (`sqlite-vec`).
   - Production: **pgvector** inside PostgreSQL.
4. **Memory Partitioning & Hygiene**:
   - Strict separation between raw conversation history, working context, and verified long-term memory.
   - All long-term facts must record source provenance (e.g., conversation ID, document reference, timestamp).
   - Support explicit user memory operations: view, search, edit, and permanent delete.

---

## 4. Consequences & Trade-offs

### Positive
- Zero external services required to start development on Windows (zero install for SQLite).
- Clean unified database in production: one PostgreSQL instance stores relational data, agent checkpoints, and vectors.
- Eliminates framework overlap and dual-write synchronizations.

### Negative / Mitigations
- SQLite lacks native concurrent writers for multi-threaded access. *Mitigation*: Enable Write-Ahead Logging (WAL mode) and route database access through a unified async connection pool.

---

## 5. Reversal Conditions

This decision would be reconsidered if vector retrieval benchmarks on corpora exceeding 500k documents show query latency degradation > 200ms on pgvector, in which case Qdrant would be adopted via an ADR.
