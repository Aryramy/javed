# ADR-003: Agent Orchestration Runtime & Execution Engine

> **Status**: PROPOSED (PENDING OWNER APPROVAL)  
> **Date**: 2026-10-22  
> **Deciders**: Principal Architect & AI Agent Lead (Subject to Project Owner Review)  
> **Impact Area**: Agent Core, State Machine, Tool Execution, Subagents  

---

## 1. Context & Problem Statement

Project **Javed (New JARVIS)** requires an autonomous multi-step agent runtime capable of:
1. Dynamic planning, reasoning, and reflection (Think -> Plan -> Act -> Observe).
2. Complex branching, loops, and conditional tool routing without building a redundant bespoke agent loop.
3. Persistent checkpointing (saving agent graph state at every step for crash recovery and session resumption).
4. Modern Human-in-the-Loop (HITL) pause and resume mechanics for consequential tool execution.
5. Granular event streaming (streaming intermediate tokens, tool call parameters, and state changes to the UI).
6. Controlled delegation to specialized subagents without combinatorial state explosions.

We critically evaluated two leading orchestration frameworks:
- **Option A**: **Deep Agents** as the primary agent harness + **LangGraph** as the underlying execution runtime + **LangChain Core** for model/tool interfaces.
- **Option B**: **CrewAI** (multi-agent role-playing framework).

---

## 2. Options Considered & Evaluation Criteria

| Evaluation Criterion | Option A: Deep Agents + LangGraph | Option B: CrewAI |
|---|---|---|
| **Primary Agent Harness & Loop** | **Built-in & Integrated**: Deep Agents provides the high-level planning harness, memory integration, and execution patterns. We avoid building a duplicate custom agent loop. | **Role-Oriented**: Focuses on multi-agent role-playing "crews" (agents, tasks, crews) with sequential or hierarchical task assignment. |
| **State Checkpointing & Resumption** | **First-Class**: Native checkpoint savers (`MemorySaver`, `SqliteSaver`, `PostgresSaver`). Supports time-travel, replay, and recovery from process crashes. | **Bespoke / Custom**: Checkpointing is less central; persistence often tied to bespoke storage or memory managers. |
| **Modern Human-in-the-Loop (HITL)** | **State-of-the-Art**: Native `interrupt()` and `Command(resume=...)` API in LangGraph v0.2+. Stateful, thread-keyed pause and resume. | **Basic Prompts**: Human input primarily through CLI console hooks or custom callbacks; lacks stateful graph interrupt/resume primitives. |
| **Real-Time Streaming** | **Granular**: `astream_events` (v2) streams LLM tokens, node transitions, and tool inputs/outputs with structured event payloads directly to UI. | **Callback-Based**: Requires custom callback handlers; less granular token-level event emission. |

## 3. Decision

We propose adopting **Option A: Deep Agents on top of LangGraph and LangChain Core** as the primary agent orchestration runtime for Javed.

### Framework Responsibilities:
1. **Deep Agents as Primary Harness**: Deep Agents provides the primary agent harness, prompt optimization, context curation, planning templates, and high-level autonomous task execution. We do **not** build a redundant second agent loop. Built-in functionality satisfies core requirements; custom LangGraph nodes and workflows require explicit justification.
2. **LangGraph as Execution Runtime**: LangGraph serves as the underlying cyclic graph state machine, managing graph execution, state transitions, checkpointing, and human-in-the-loop interruptions.
3. **LangChain Core as Model & Tool Interface**: Provides standardized `ChatOpenAI`-compatible model adapters and `@tool` schema decorators.

### Rejection of CrewAI:
While CrewAI is a capable, open-source (MIT) framework for simulating collaborative teams of distinct personas, its role-playing abstractions do not align with our requirement for a single, unified personal assistant controlling deterministic tools, persistent checkpoints, and low-level interruption protocols. Adopting both would violate Rule 11 (No Overlapping Frameworks).

## 4. Modern LangGraph Human-in-the-Loop (HITL) Specification

We standardize on LangGraph's modern human-in-the-loop API (`interrupt()` and `Command(resume=...)`), explicitly addressing checkpointing, thread identity, and side-effect replay safety:

### 4.1 Checkpoint & Thread Identity Requirements
- **Mandatory Checkpointer**: LangGraph's `interrupt()` strictly requires an active checkpointer (`SqliteSaver` in development, `PostgresSaver` in production). If a graph attempts to interrupt without a checkpointer, LangGraph raises a runtime error because state cannot be saved.
- **Thread Identity**: Checkpoints and pauses are keyed to a specific thread ID:
  ```python
  config = {"configurable": {"thread_id": session_id}}
  ```
  The resume command must be dispatched with the identical `thread_id` to restore the paused state.

### 4.2 The Interrupt and Resume Protocol
1. **Interrupting**: Inside a tool-gating node, when a Tier 3 action is evaluated, the host code calls:
   ```python
   approval = interrupt({
       "action": "shell_execution",
       "command": tool_call["args"]["command"],
       "risk": "Tier 3: High Risk",
   })
   ```
   LangGraph pauses execution immediately, serializes state to the database, and returns the dictionary payload to the client.
2. **Resuming**: When the user approves in the UI, the client sends an approval token. The gateway invokes the graph with:
   ```python
   graph.invoke(Command(resume={"approved": True}), config=config)
   ```
   The value passed to `Command(resume=...)` becomes the return value of the `interrupt()` call inside the node.

### 4.3 Mitigation of Side-Effect Replay Risk
> [!IMPORTANT]
> **Understanding LangGraph Node Re-Execution**:
> When a graph resumes from an `interrupt()`, LangGraph re-runs the node function containing the `interrupt()` call from its first line of code.
> When execution reaches the `interrupt()` line, instead of pausing, LangGraph returns the resume payload provided by `Command(resume=...)`.
> 
> **The Danger**: If non-idempotent operations (such as database inserts, email dispatch, or external API calls) are performed *before* `interrupt()` within that same node, **they will execute a second time upon resumption**.
> 
> **Architectural Invariant**:
> 1. The node containing `interrupt()` must be strictly **pure and idempotent**. It must only construct approval metadata and call `interrupt()`.
> 2. All actual side effects (e.g. running the shell command, writing to disk, mutating state) must reside in a separate downstream node that executes **after** the interrupt node has validated the user's approval.

## 5. Consequences & Trade-offs

### Positive
- Built-in planning and execution loop via Deep Agents avoids custom agent loop bugs.
- Resilient crash recovery: Tasks survive server restarts via SQLite/PostgreSQL checkpointing.
- Proven, safe HITL protocol that guarantees zero accidental command replay.

### Negative / Mitigations
- Requires disciplined node separation to prevent side-effect duplication on resume. Enforced through automated contract tests in `TEST_STRATEGY.md`.

---

## 6. Reversal Conditions

This decision would be reconsidered only if LangGraph introduces breaking architectural shifts that degrade local execution or if Deep Agents fails to support our required tool schema bindings.
